# Android audit — 2026-08-09

Four independent Fable reviews of the Android side: the `:beacon` sensor hub, GPS
sourcing and fallback, the telemetry/state pipeline, and offline resilience.
Every review was given the same operating reality — **Burning Man, the internet
comes and goes and mostly it is gone, 14 days unattended, 8-10 tablets, dust and
power cuts** — and this project's standing rule that a test which cannot fail is
worthless.

**Legend:** ✅ = I verified the claim against the code myself. ◻ = reported by
the review, not independently checked. Every item carries `file:line`.

Status of each item lives in `tasks/open.md`; this file is the evidence.

---

## P0 — safety-critical

### A1 ✅ The forward BRAKE alert is dead on a real drive

```
CockpitViewModel.kt:262   driverAlerts({ _uiState.value.speedKph.toFloat() })
CockpitViewModel.kt:446   _uiState.update { it.copy(speedKph = clamped) }   <- ONLY writer
SurroundRing.kt:108,312   speedKph >= BRAKE_MIN_KPH (5f)
```

`uiState.speedKph` is written by exactly one thing: `setSpeed()`, the debug chips
in the control strip. The location collector folds **heading only**; GPS speed
(`GpsFix.speedKph`, parsed from RMC at `NmeaParser.kt:167`) and the beacon's
`$ZTLM` speed never reach it. So on a real vehicle on NET GPS the gate reads 0
forever and neither `! BRAKE !` nor the `! COLLISION COURSE !` banner
(`DriverNightScreen.kt:214`) can ever fire.

`checkRear` has no speed gate, which is exactly why the 2026-08-08 bench
verification against real bus traffic passed. Corroborating symptom: the HUD's
MPH readout (`DriverNightScreen.kt:115`) reads the same field and shows 0 while
driving.

`BurnInMitigationManager.kt:136` already reads `fix.speedKph` correctly — the
codebase knows where real speed lives; the alert path just doesn't use it.

**Root cause is structural: there is no single owner of "vehicle speed."** Three
uncorrelated sources (debug `uiState.speedKph`, `egoFix.speedKph`, `$ZTLM`) and
each consumer picks one ad hoc. The next speed-dependent feature re-rolls the
same die.

### A2 ✅ The deployed build substitutes fabricated contacts when the Jetson dies

```
RoutedThreatSource.kt:33    private val demoEnabled: Boolean = true,
ZodiacApplication.kt:237    RoutedThreatSource(network=…, fake=…, scope=…)   <- not passed
```

The class doc (`RoutedThreatSource.kt:24,44-46`) states `demoEnabled=false` is
the deployed-vehicle setting so a dead feed surfaces as **ABSENT, never silently
as DEMO**. The wiring never passes it. A Jetson crash mid-drive therefore puts
`FakeThreatSource`'s three invented moving contacts on the driver's night HUD —
one of which cycles `collision=true` (`FakeThreatSource.kt:70`) — distinguished
only by a small "DEMO" status word.

The ABSENT ≠ DEMO ≠ CLEAR distinction the architecture worked to create is
**unreachable in the shipped wiring**; there is no flag or preference, only a
code edit.

⚠️ **Interacts with A1**: fixing the brake gate alone makes demo mode flash real
braking imperatives at fabricated pedestrians. Fix them together.

### A3 ✅ The S9+ GPS fallback can freeze `Active` forever

`FixFreshness` reference counts: `BleLocationSource` **4**, `UsbLocationSource`
**4**, `SystemLocationSource` **0**. SYSTEM is the fallback target inside
`FailoverLocationSource` (`ZodiacApplication.kt:194-201`), and the failover
judges the fallback usable by its state being `Active`
(`FailoverLocationSource.kt:81`) — which a frozen state satisfies indefinitely.

`SystemLocationSource.kt:89-90` publishes `Active` only from
`onLocationChanged`; nothing demotes it. `onProviderDisabled` is a default no-op
(the listener is a SAM lambda), so the provider being switched off is silent.
`FixFreshness.kt:17-20` documents this exact failure mode and records that the
fix was applied to BLE and USB — SYSTEM was missed.

Beacon dies → failover engages correctly → S9+ loses sky (dash mount, dust) →
last fix stays `Active` forever. Map, drive-to guidance and street-crossing cues
all steer off it, and by the project's **no-badge decision** nothing on screen
indicates backup GPS at all.

## P1 — unattended recovery and crash loops

### B1 ◻ Corrupt DataStore prefs → boot crash-loop on a kiosked tablet

`ZodiacApplication.kt:140-144` creates the prefs DataStore with **no
`corruptionHandler`**. A file torn by a power cut makes `dataStore.data.first()`
throw `CorruptionException`, and `preferences.read()` is the *first statement* of
the ViewModel init (`CockpitViewModel.kt:148`) inside a launch with no catch →
uncaught → process death, every launch. Same read fires from `DisplayRoleStore`
(`core/passenger/DisplayRoleStore.kt:29`) and the burn-in config store.

On a kiosked Fire (status bar disabled, lock task) there is **no Settings access
to clear data** — recovery is adb or factory reset. One line fixes it:
`ReplaceFileCorruptionHandler { emptyPreferences() }`.

Follow-on trap: recovery-to-defaults selects `FAKE` (`CockpitPreferences.kt:33`),
so the tablet returns driving on synthetic GPS that renders a plausible live map
parked at Golden Spike.

### B2 ◻ `BurnInConfig.coerced()` throws at the timeout ceiling

`burnin/BurnInConfig.kt:66-67` — if `dimTimeoutSec` coerces to `MAX_TIMEOUT_SEC`,
the next line calls `coerceIn(MAX+1, MAX)`, an empty range, which throws. Reachable
from the tuning panel's unbounded "+" buttons (`BurnInTuningPanel.kt:135,155,168`)
and from persisted values at startup (`DataStoreCockpitPreferences.kt:71-90`) —
i.e. **another boot crash-loop**. The class doc promises "a tampered or stale
persisted value can never seed an out-of-range config".

`BurnInConfigTest` only exercises small inverted values (1000/500/100) — it never
approaches the boundary where the failure lives.

### B3 ✅ Beacon has no boot receiver — a reboot leaves the fleet with no GPS

`TelemetryService` starts only from `BeaconActivity.onToggle`
(`BeaconActivity.kt:83-92`). No `RECEIVE_BOOT_COMPLETED` anywhere in the module
(grep: zero hits). `START_STICKY` (`TelemetryService.kt:29`) covers process
death, not reboot. A 12 V brownout or thermal reboot → beacon stays off → every
tablet is blind until a human picks up the phone.

### B4 ✅ `WAKE_LOCK` declared, never acquired

Declared at `beacon/src/main/AndroidManifest.xml:13`; grep finds **zero**
`PowerManager`/`newWakeLock` usages. A foreground service does not keep the CPU
awake. Charging fault → screen-off, unplugged, stationary → Doze stalls the
`delay(250)` tick loop (`TelemetryBroadcaster.kt:208`): heading freezes and
`$ZBCN` gaps make tablets think the beacon died — intermittently, only when the
charger is flaky.

### B5 ◻ Beacon FGS types vs permissions

`AndroidManifest.xml:39` declares `foregroundServiceType="location|microphone"`
and `TelemetryService.kt:21` uses the 2-arg `startForeground` (= all declared
types). On Android 11+ a location-type FGS restarted while backgrounded (exactly
a `START_STICKY` restart) gets **no location updates**; on Android 14+, starting
with the microphone type while `RECORD_AUDIO` is denied throws `SecurityException`
— so "mic is optional" is false on 14+. The XCover Pro (Android 10) dodges both;
a replacement phone would not. Also `TelemetryBroadcaster.start` is
`@SuppressLint("MissingPermission")` (`:145`) and calls `requestLocationUpdates`
(`:181`) unguarded → `SecurityException` in `onCreate` → START_STICKY restarts
into the same crash.

### B6 ◻ One exception kills every synthesized channel, silently

The 250 ms tick loop (`TelemetryBroadcaster.kt:195-210`) has no try/catch. Any
throw ends the coroutine; GNSS passthrough keeps flowing on the listener
(`:182`), `_running` stays true, and HDT/ZTLM/ZENV/ZODO/ZBCN just stop with
nothing on the phone saying so.

## P2 — silently wrong data

### C1 ✅ Beacon lux defaults to `0.0` and is broadcast as real

`TelemetryBroadcaster.kt:118` initialises `luxValue = 0.0` and `:200` sends it.
A device with no light sensor never registers one (`:191`, `?.let`) so **0.0 lux
broadcasts forever** → `luxToBrightness(0.0)` = 0.05 → the whole fleet pinned to
5% brightness in daylight. Same class: no rotation-vector sensor → `$GPHDT,0.0`
forever and every drive-to arrow points wrong. There is no "channel absent"
semantic — a missing sensor should suppress the sentence, not emit zero.

### C2 ◻ Auto-dim and burn-in fight over screen brightness; auto-dim wins

Two uncoordinated writers to `window.attributes.screenBrightness`:
`MainActivity.kt:187-195` (on every lux change) and `BurnInScaffold.kt:97-101`
(on phase transitions). The beacon broadcasts `$ZENV` continuously, so auto-dim
re-fires within seconds of any burn-in transition: DEEP_IDLE's 0.15 backlight
and SLEEP's 0.01 are both overridden back to the lux curve. **The burn-in
mitigation is defeated whenever the beacon is live** — which is always, on a
fleet vehicle. No arbiter exists; the two features were verified independently.

### C3 ◻ Burn-in animation clock freezes after ~3-6 days

`BurnInScaffold.kt:114-124` accumulates `tSec: Float += delta`. At t ≈ 2^19 s
(~6.1 days) the Float ULP exceeds a 60 fps frame delta, so `+=` rounds to zero
every frame and the clock stops — permanently. On the 120 Hz S9+ that arrives
around 3 days; quantisation degrades the shift path from ~1.5 days. Pixel shift
parks at a fixed offset and the brightness breathe flatlines, silently, for the
rest of a 14-day event. The phase machine itself is fine (`elapsedRealtime`,
Long, jump-immune).

### C4 ◻ NET `stop()` freezes beacon sensors as live-looking state

`NetworkLocationSource.kt:151-162` cancels the silence watchdog and closes the
socket but never clears `_beaconSensors`, `_telemetry`, `_audioLevel`. The
watchdog (`:130-145`) is the only thing that clears them, and `stop()` kills it
without doing its job. Switch off NET at night → `ambientLux` frozen low →
auto-dim holds the screen at the 0.05 floor **through the next day**, plus a dead
beacon's battery/sats/uptime shown as current. The ViewModel takes
`networkLocationSource.beaconSensors` unconditionally (`MainActivity.kt:118`),
regardless of the selected source.

### C5 ◻ ViewModel init double-starts the persisted source; multicast lock leaks

`CockpitViewModel.kt:296-301` calls `select(saved)` then `start()`. `select`
already starts it (`RoutedLocationSource.kt:78-80`) and `start()` has no guard
(`:66-70`). The comment claiming "re-entry guarded" is true only for SYSTEM and
FAKE. `NetworkLocationSource.start()` (`:115-120`) is unguarded, and
`acquireMulticastLock()` (`:171-176`) **overwrites `multicastLock` without
releasing the old one** (`setReferenceCounted(false)`), so the leaked lock keeps
the WiFi multicast filter disabled for the process lifetime. Every fleet tablet
persists NET, so **this path runs on every launch**.

### C6 ◻ `VTG` and `HDG/HDM` treated as compass heading

`NmeaParser.kt:52` matches `HDT|HDG|HDM|VTG` identically, and
`NetworkLocationSource.kt:262` *prefers* that value over RMC course "because the
compass is valid when stopped". But VTG **is** GPS course, and Android GNSS chips
emit it every epoch through the beacon's verbatim passthrough. Stopped vehicle →
heading flip-flops between real compass and course noise. Worse, VTG keeps
`headingRxMs` fresh, defeating the dead-compass watchdog that exists to fall back
to course. HDG/HDM are magnetic (~13°E declination at BRC) and the variation
fields are discarded.

`NmeaParserTest.kt:74-78` **asserts this behaviour**, locking the bug in — the
project's third instance of a test agreeing with a bug.

### C7 ◻ Shock events double-count; shock reports first crossing not peak

- Beacon sends every sentence to both multicast and subnet broadcast
  (`TelemetryBroadcaster.kt:162`), and the tablet binds wildcard **and** joins
  the group (`NetworkLocationSource.kt:194-203`) — on an AP that forwards
  multicast every datagram arrives twice, so `shockCount`
  (`NetworkLocationSource.kt:280-282`) is 2× and it is AP-dependent.
- `ShockDetector.kt:28-32` returns the first over-threshold sample and arms the
  500 ms refractory, swallowing the actual peak. Docs promise peak magnitude.

### C8 ◻ Odometer counts multipath teleports

`TripOdometer.add` accepts any step ≥ 5 m (`:40-46`); `loc.accuracy` and
`loc.speed` are never consulted and there is no max-step gate. Parked among RVs
for days, multipath accrues phantom km on trip **and lifetime**, and a bad
cold-start fix hundreds of km out is added and **persisted permanently**
(`TelemetryBroadcaster.kt:382`).

### C9 ◻ Discovery cache: purgeable location, non-atomic write, clobber on partial fetch

- `ZodiacApplication.kt:274` puts the **only offline copy** of art/camp data in
  `cacheDir`, which Android trims under storage pressure. Belongs in `filesDir`.
- `DiscoveryRepository.kt:90` uses `writeText` — truncate-then-write, no
  tmp+rename. `PlayaMapBinaryCache.write` (`:92-110`) already does it correctly.
- `DiscoveryRepository.kt:57-59` overwrites cache on any *non-empty* result, so a
  fetch where camps all fail to parse but art survives destroys the last good
  full dataset.
- `BmApiClient.kt:44-46` projects any finite lat/lon with no plausibility gate —
  swapped or zeroed coordinates paint markers kilometres off-city.
- Zero logging in the whole discovery path — "why are there no art markers" is
  unanswerable from the on-device viewer, which on Fires is the only tool.

### C10 ◻ `mapLoadError` is dead state

`CockpitViewModel.kt:196` sets it, `CockpitUiState.kt:63` declares it, nothing
renders it. `MapLoadResult.kt` promises "surface a human-readable error … instead
of silently displaying a blank map"; unimplemented. The next silent GIS schema
change gives a blank viewport with no message and no retry.

## P3 — correctness and hygiene

- ◻ **Log overflow is silent** — `FileLogTree.kt:40,59` never counts `DROP_OLDEST`
  evictions, so the viewer's `DROPPED` badge (`LogViewerPanel.kt:158`, comment:
  "Silent loss would make the log a liar") lies during the bursts that matter.
- ◻ **`RollingFileLog.rotate()` ignores `renameTo` failures** (`:118-131`),
  breaking the class's "total size is bounded" contract.
- ◻ **`ThreatProtocol` drift is enforced socially, not mechanically** — two
  hand-mirrored implementations and two hand-mirrored test suites in one repo,
  zero shared artifacts. Ids > 2^31 silently drop on the Kotlin side; out-of-range
  az is dropped rather than wrapped on both.
- ◻ **NET `Error` is terminal** (`NetworkLocationSource.kt:204-224`) — no retry;
  recovery needs a human toggling the chip. `joinGroup` happens once (`:202`) with
  no rejoin after a router reboot. BLE has the same terminal-state shape
  (`BleLocationSource.kt:143`).
- ◻ **GGA wipes speed out of the merged fix** (`NetworkLocationSource.kt:251-254`)
  — `lastFix` is replaced wholesale rather than merged, so alternate fixes carry
  `speedKph = null`.
- ◻ **Beacon network targets computed once** (`TelemetryBroadcaster.kt:162`) —
  start before the router is up and the fallback is `255.255.255.255` forever;
  socket is never bound to the WiFi `Network`, so traffic can leave the wrong
  interface with no error while status says "Broadcasting".
- ◻ **`$ZAUD` dies permanently on one transient read error**
  (`TelemetryBroadcaster.kt:342`, `if (n <= 0) break`) and the status keeps
  showing a stale rms afterwards.
- ◻ **Send reordering + racy counter** — one coroutine per sentence onto the IO
  pool (`:271-283`), non-atomic `sentences++`.
- ◻ **Kiosk**: `docs/KIOSK.md:34` provisions with `app-debug.apk` — a device-owner
  app can't be uninstalled and updates must match signature, so a later
  release-signed update means a factory reset per tablet. The documented escape
  hatch `dpm remove-active-admin` (`:56`) only works for `testOnly` apps, which a
  plain debug APK is not. `KioskController.engage` (`:60-70`) bundles four
  policies in one `runCatching`, and `ota_disable_automatic_update` is not an
  allowed key on API 34 — so the "no OS update at 2am" guarantee likely does not
  hold on the Samsungs despite the log saying setup ran.

## Tests that agree with the code they test

The project's named anti-pattern, found again in four places:

1. ✅ **`Nmea.checksum` was validated against itself** — `xor` → `or` (and → `+`)
   passed all 35 beacon tests. **FIXED 2026-08-09** with published NMEA 0183
   reference vectors; both mutants now die.
2. ◻ **`NmeaParserTest.kt:74-78`** asserts VTG/HDG parse as compass heading —
   locks in C6, and even supplies a magnetic variation the assertion ignores.
3. ◻ **`PlayaMapBinaryCacheTest.kt:79`** writes `..._v1.bin` while `fileFor()`
   reads `..._v2.bin`, so the test passes through the file-missing branch and the
   magic/version/truncation checks are entirely unverified — delete the header
   check and it stays green.
4. ◻ **`NavTargetTest.kt:22-26`** repeats the Temple coordinate literal, so it can
   only agree with a wrong one. Should be a `BundledGisTest`-style ground-truth
   check against the shipped GeoJSON.
5. ◻ **`SurroundRingTest` band-boundary tests** assert behaviour against the same
   named constants the implementation uses.
6. ◻ **`BurnInConfigTest`** never approaches the ceiling where B2 lives.
7. ◻ **`SystemLocationSourceTest`** — all eight tests are lifecycle/permission
   accounting; not one delivers a `Location`, which is how A3 survives 719 green
   tests.

## Structural — what slows shipping down

- **No single owner of vehicle speed** (three sources) → A1.
- **No single owner of window brightness** (two writers) → C2.
- **Staleness implemented three ways**: `FixFreshness` (BLE/USB), an inline
  watchdog (NET), nothing (SYSTEM). One mechanism, one definition, one suite.
- **`NetworkLocationSource.ingest()` is private behind a real socket** — the pure
  core worth testing. Extracting it collapses ~12 multi-second socket tests into
  instant deterministic ones.
- **BLE/USB sources are untestable by construction** — no handle seam, already
  bitten once per `FixFreshness.kt:17-20`.
- **`object TelemetryBroadcaster` is a 408-line process singleton** owning socket,
  sensors, GPS, audio, prefs and scheduling — which is why every beacon bug above
  has no test. The `BeaconNet` extraction is the right pattern, half-done.
- **`beacon` is exempt from the lint gate** (`beacon/build.gradle.kts:35-37`,
  `abortOnError = false`) — and manifest FGS/permission mistakes (B5) are exactly
  what Android Lint catches, on the one module where they are fleet-fatal.
- **Deployment truths are compile-time**: `demoEnabled`, `COVERED_ARCS`, fleet-bus
  group/port. Every change is an APK.
