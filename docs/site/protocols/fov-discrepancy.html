Known discrepancy: the field-of-view reference

RESOLVED 2026-08-10 — this page is now history, not a live warning

zvision's --fov-ref now defaults to d (rig.CameraMount and the CLI), so both sides of the vehicle compute ±64° by default. FovReferenceDefaultTest pins it, and both mutations were run — reverting either default turns the suite red.

The diagonal reading was confirmed physically. A cold target at 85 cm off centre at 1.0 m (a true 40.4°) was reported by the running rig at 42.5° — implying a ~61° horizontal half-FOV, against 64° assumed, which agrees to about 5%. Had the 160° been horizontal (80° half-FOV) the same contact would have been reported at 32.3°. ±80° is ruled out by observation, not by argument.

Note also that the deployed rig always passed fovref=d explicitly, so the running vehicle never carried this error. The exposure was latent: the next camera added to the rig without the flag would have inherited ±80°. The argument below is retained because it is what led to the measurement.

The tablet and the edge box currently disagree about how wide the forward thermal camera sees. The consequence is up to 16° of bearing error at the frame edge — on the number that both draws the driver's HUD and aims a spotlight at a person.

Open — recorded, not fixed

This is a code decision, not a documentation one. It is written down so that anyone reading a bearing off the bus knows the edge values are unverified until it is resolved.

What the two sides believe

SideBelieves the forward thermal coversWhere
Tablet (:app)±64°SurroundRing.COVERED_ARCS = -64f..64f
Edge box (zvision)±80°--fov-ref defaults to h; geometry.FOV_HORIZONTAL; rig.CameraMount.fov_ref

Every documented example rig — in jetson/README.md, jetson/DEPLOY.md, jetson/HARDWARE.md and jetson/TRAINING.md — omits fovref=d, so following any of them reproduces the ±80° reading.

Why ±64° is the settled reading

FLIR never states which axis the Lepton Ultra Wide's quoted 160° refers to — the product page, GroupGets, and the R200 dewarping note all just say “160°”. So it was settled on physics rather than on a document:

  • The board emits 160×120 — a 4:3 frame, measured on the real board on 2026-08-07 (it had first been recorded as 120×120).
  • 160° across the width of a 4:3 f-theta frame would demand a ~200° diagonal — not a lens that exists. On the square 120×120 “usable” area FLIR quotes, it would be 226°.
  • Read as the diagonal, it is an ordinary fisheye and the true horizontal half-angle is 80° × 80/100 = 64°. The camera covers ±64°, not ±80°.

LeptonUwFovReferenceTest pins that arithmetic, and the tablet's SurroundRing.COVERED_ARCS carries the matching ±64°.

Why it is not cosmetic

fov_ref feeds pixel_to_bearing, so the wrong choice mis-aims every edge bearing by up to 16° — about 2.8 m of miss on a person 10 m away, which is exactly where the tracker light gets pointed.

The policy behind the choice

Under uncertainty, under-claim coverage

Under-claiming coverage costs a little caution. Over-claiming is the confident all-clear that the blind-arc report exists to prevent. Widen the arc only against a real measurement, or a FLIR figure that names the axis.

What resolving it looks like

Either the Python default flips to d, or the tablet's covered arc widens. Until one of those happens:

  • Add fovref=d by hand to the thermal camera's --camera spec if you want the two sides of the vehicle to agree.
  • Treat edge bearings as unverified.
--camera thermal:/dev/video0:az=0:fov=160:fovref=d:lens=fisheye:name=thermal

A second, unreconciled number

Unreconciled — optics, not bearings

The germanium window sizing in jetson/HARDWARE.md uses an 80° half-angle (required radius ≈ standoff × tan 80° ≈ standoff × 5.7), giving a ~1.7–2 mm maximum standoff for the ordered D20 window. The FOV-reference decision concludes the true horizontal half-angle is 64° (tan 64° ≈ 2.05), which would allow roughly 4.9 mm of standoff for the same window.

The optics number was not revised when the bearing number was. The 2 mm figure is the conservative one, so building to it is safe — but the 5.7× rule should not be quoted elsewhere without deciding which half-angle applies.
