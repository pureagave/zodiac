:beacon — the sensor hub

Package org.pureagave.zodiac.beacon. A headless foreground-service app that turns a spare Android phone into the vehicle's shared sensor. minSdk 29, because the XCover Pro it runs on is Android 10. One foreground service, one debug activity, no resources — the UI is built in code.

What it broadcasts

It forwards the phone's raw GNSS NMEA verbatim and adds seven synthesized sentence types.

SentenceCarriesRate
$GPHDTTrue compass heading (magnetometer, declination-corrected once a fix exists)~4 Hz
$ZTLMIMU pitch/roll + ground speed~4 Hz
$ZAUDMic level — rms, peak, beat flag~15 Hz
$ZENVAmbient lux~0.5 Hz
$ZSHKShock / impact peak gOn impact
$ZBCNHealth — battery %, fix quality, satellites, uptime~0.2 Hz
$ZODOTrip + lifetime odometer (persisted)~0.5 Hz

Every sentence goes to multicast group 239.7.7.10:10110 and a subnet-directed broadcast. Field-by-field definitions →

Design rules that matter operationally

Only a level number ever leaves the phone

No audio is recorded, buffered to disk, or transmitted — the PCM buffer is reduced to three scalars in place and discarded. The microphone is optional at every layer, and a boot-started service never requests it at all.

  • Every sentence is sent twice, because some access points drop multicast. That is why the tablet de-duplicates byte-identical $ZSHK lines inside a 200 ms window.
  • GPS failure is never fatal. If location permission is missing or wiring throws, every other channel keeps broadcasting and the notification says so.
  • A sensor the phone does not have emits nothing rather than a fabricated zero — for heading and lux. A fabricated 0.0 lux would pin the whole fleet to 5 % brightness in daylight. A genuine 0.0 lux or 0.0° heading is still emitted.
  • The odometer refuses implausible steps — inaccurate (> 20 m), below a 5 m jitter floor, or implying more than 160 kph — so GPS multipath cannot inflate the trip.

Where it runs

On the XCover Pro (SM-G715U) today, headless with the screen off, holding a partial wake lock. It has a debug activity showing the live status readout, but that is for bring-up only.

Planned replacement: a Raspberry Pi Zero 2 W with a u-blox USB GNSS receiver and a roof antenna. The travel router keeps the AP and DHCP role in both cases. Device notes →

On-device verification still owed

None of these can be proven in CI — the phone is API 29 and Robolectric models the API contract, not real OS scheduling.

  • Reboot test — start the beacon, adb reboot, confirm $ZBCN reaches a tablet within ~90 s with zero phone interaction.
  • Sideloaded update — install a new signed APK over a running beacon and confirm MY_PACKAGE_REPLACED restarts it.
  • No lock-screen credential on the beacon phone. BOOT_COMPLETED only fires after first unlock on file-based-encryption devices.
  • Battery-optimization prompt appears once and never re-nags after a decline.
  • Doze / charger-loss soak — confirm the wake lock actually prevents the tick-loop stall. Cannot be simulated.
  • API 30+ two-step background-location grant. Untestable on API 29.
  • API 34/35 typed startForeground. Argued from documentation, not observed. The biggest untested-on-hardware risk in this module.
Needs a decision — direct boot

On a file-based-encryption device with a secure lock screen the boot receiver never fires, so a 3am thermal reboot would leave the fleet blind until someone physically unlocks the phone. Either confirm the beacon phone has no secure lock credential, or make the receiver and service direct-boot-aware (which also moves the auto-start preference to device-protected storage).

Outstanding — interface binding

Beacon network targets are computed once and the socket is never bound to the WiFi Network, so traffic can leave the wrong interface silently.
