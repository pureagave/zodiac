jetson/ · the edge box

Bring-up runbook

From box to broadcasting live threats on the vehicle bus. The design goal: every stage is verifiable on its own. You prove the network path with --source fake before a camera is ever attached, so if something breaks later you know it is the camera, not the bus.

Checklist

  1. Flash JetPack 7.2 / L4T 39.2 to the NVMe from the Linux flash host, first boot, confirm MAXN Super
  2. Network: Ethernet → travel router; note the Jetson's IP for --iface-ip
  3. Install: sudo jetson/scripts/install.sh
  4. Prove the bus, no camera: python3 -m zvision --source fake -v → a tablet's DRIVER HUD shows the moving demo. This is the big one.
  5. Attach camera(s): v4l2-ctl --list-devices, then --source thermal, and walk in front of it
  6. Make permanent: set the real source in /etc/default/zvision, systemctl restart zvision
  7. (optional, any time) DMX light: sudo jetson/scripts/install-ola.sh, patch the dongle, --dmx ola

Before starting, run the read-only pre-flight on the flash host: jetson/scripts/preflight-flash.sh checks the BSP staging, the host tools, the qemu-aarch64-static symlink, the baked-in user, the t234 flash XML and free space. --command prints the exact flash command. It changes nothing.

Software status, honestly

The bus, the rig, the broadcaster and the tracker are built and tested, and the box can boot straight into them. Two things are not finished and are not software bugs: the tracker light's aim constants are uncalibrated placeholders that must be set on the actual mount before enabling --dmx ola, and DMX arbitration between zvision and zodiac-deck is unresolved — do not run both with real DMX output.

1. Flash JetPack

Not SDK Manager. It is a GUI app, useless over SSH, and its supported hosts are Ubuntu 20.04/22.04. The Jetson Linux BSP's own CLI flasher — which SDK Manager only wraps — is used instead: no GUI, no NVIDIA login, headless, and it is the documented path for external NVMe.

The flash host is an x86 Ubuntu machine. A Mac cannot do this — Tegra recovery is a USB protocol and needs an x86 Linux host. JetPack 7.2 / L4T 39.2 rather than 6.x because r39.2 added Orin Nano Dev Kit support and its newer toolchain is more tolerant of a newer host.

Host setup gotchas

nfs-kernel-server is required, not optional

l4t_initrd_flash.sh boots a small initrd on the Jetson and serves the rootfs to it over the USB link via NFS, so the flash aborts immediately without it. (An earlier note said it was optional, on the strength of exportfs being guarded by command -v in one code path — that guard is real and the requirement is still hard.)

Modern OpenSSH breaks the recovery-image build

L4T's ota_make_recovery_img_dtb.sh calls ssh-keygen -t dsa, and OpenSSH ≥ 9.8 removed DSA entirely. The failure lands on a bare check_error, so all you see is command is failed / Error: failed to generate images with no hint. Comment that one line out — the initrd's sshd config only ever references rsa/ecdsa/ed25519, so the DSA key it generates is never used.

Also: on 26.04 qemu-user-static no longer exists — it is qemu-user (still static-pie linked), and L4T's scripts hard-code the -static name, hence a symlink. And apt aborts the whole transaction on one bad package name, so a typo silently installs nothing; verify with dpkg -s.

Bake in the login before flashing

A stock image first-boots into oem-config, the interactive account wizard — with no monitor attached the Jetson just sits there and looks like a failed flash. Pre-seed the account instead:

sudo ./tools/l4t_create_default_user.sh -u <user> -p <pass> -n <hostname> --accept-license

Force Recovery

J14 button header, on the board edge under the module. Read the silkscreen, do not count pins — authoritative pinout from carrier board spec SP-11324-001, Table 3-4:

PinSignalPinSignal
1PC_LED−7GND
2PC_LED+8SYS_RESET*
3UART2_RXD (debug, 3.3 V)9GND
4UART2_TXD (debug, 3.3 V)10FORCE_RECOVERY*
5AC OK11GND
6Auto-Power-On disable12SLEEP/WAKE* (power button)

No pin carries a supply rail, so a slip onto a neighbouring pair is at worst a reset or a power-button press — not damage. The kit ships no jumpers; ATX front-panel momentary switches fit (2.54 mm, 2-pin female) and are far easier than a jumper cap in that cramped spot.

  1. Board unpowered. NVMe seated in the M.2 Key-M slot — the kit ships with no storage, and without it the flash has no target.
  2. Bridge FC_REC ↔ GND (pins 10 ↔ 9).
  3. USB-C from the Jetson's C port (J5, the only port that can flash; the Type-A ports are hosts) to the flash host.
  4. Plug in the 19 V barrel jack — it powers on automatically, straight into recovery.
  5. Release FC_REC.
  6. Confirm: lsusb | grep 0955 → 0955:7523.

Already powered? Hold FC_REC, tap RESET (pins 8↔7), release FC_REC. With two buttons fitted you never touch the power cable — and recovery is repeatable, which matters during bring-up.

Flash

sudo ./tools/kernel_flash/l4t_initrd_flash.sh \
     --external-device nvme0n1p1 \
     -c ./tools/kernel_flash/flash_l4t_t234_nvme.xml \
     --showlogs --network usb0 \
     jetson-orin-nano-devkit-super internal
  • t234 = Orin. (t264 is Thor — wrong file, do not grab it by mistake.)
  • --network usb0 runs the bulk transfer as ethernet-over-USB, which NVIDIA notes is more reliable than raw USB. Still just the one USB-C cable.
  • internal as rootdev writes QSPI as well as the NVMe. Going from shipped firmware to r39.2 is a big jump, so the bootloader update matters — do not interrupt the flash, a half-written QSPI is the one way to brick it.
  • Add --no-flash to build the images with no board attached, which de-risks the toolchain before you are standing there holding a button.
You can reach it over the flash cable

The Jetson brings up a USB gadget network on first boot and answers at 192.168.55.1. That works before any DHCP lease exists, and it is the quickest way in if Ethernet is not ready.

Power mode

sudo nvpmodel -p --verbose | grep POWER_MODEL   # list the IDs first
sudo nvpmodel -m 2        # MAXN_SUPER on JetPack 7.2
nvpmodel -q               # confirm: "NV Power Mode: MAXN_SUPER"
The mode ID is not 0

On JetPack 7.2 / L4T 39.2 the table is 0=15W · 1=25W · 2=MAXN_SUPER, and the board ships on 1. This runbook previously said -m 0, which sets the slowest mode — following it left the box slower than stock while reporting success. Verified on the real board 2026-08-06: MAXN_SUPER took GPU max 612 → 1020 MHz and CPU 1497 → 1728 MHz. Always list the modes rather than trusting an ID.

It reverts on every reboot unless the default in /etc/nvpmodel.conf is changed.

OpenCV

Not preinstalled — import cv2 fails on a fresh JetPack 7.2. Only the fake source is stdlib-only, so the bus can be proven without it; any real camera needs it.

sudo apt-get install -y nvidia-opencv libopencv-python

nvidia-opencv alone installs the C++ libraries but not the Python bindings — libopencv-python is the package that provides cv2. Still do not pip install opencv-python: the apt build is the one matched to this JetPack, and pip would shadow it. Note it reports zero CUDA-enabled devices and carries no CUDA in its build info — fine, since the motion detector is pure CPU work and a trained model will run through TensorRT, not OpenCV CUDA.

Serial console backstop

J14 pins 3/4 are a 3.3 V debug UART. A CP2102 USB-TTL cable gives console into the Jetson from anywhere — worth wiring for a box that lives headless in a vehicle. Crossover: adapter TXD→pin 3, RXD→pin 4, GND→pin 7/9/11, 5 V lead unused. 115200 8N1. Receive-only (RXD+GND) gets the full boot log with zero risk to the board.

2. Get it on the vehicle network

Ethernet to the travel router is the most reliable for a fixed roof install. Alternatives: an Intel AX210 in the M.2 Key-E slot with two antennas, or a USB WiFi dongle.

Multicast across a wired ↔ wireless bridge

If the Jetson is wired and the tablets are wireless, some routers drop multicast at the bridge (IGMP snooping). zvision already sends a subnet-broadcast copy of every frame, so it works regardless — but if you ever see fake threats on a same-band test and nothing across the bridge, that is the cause, and the broadcast leg is the fix.

3. Install zvision

Clone directly into /opt/zodiac — the same path the service runs from, so there is exactly one copy of the code on the box and git log always answers “what is actually running”. Before that discipline the box carried two untracked copies that had silently drifted four days behind main, and nothing on the box could tell you that.

sudo mkdir -p /opt/zodiac && sudo chown "$USER:$USER" /opt/zodiac
git clone https://github.com/pureagave/zodiac.git /opt/zodiac
cd /opt/zodiac
sudo jetson/scripts/install.sh

This installs a systemd service and a config file at /etc/default/zvision — outside the repo, so a git pull never clobbers the rig's configuration.

What install.sh does not do
  • It enables and starts the service immediately, configured to --source fake --hz 10 — which means it broadcasts three synthetic contacts, one a recurring phantom collision, to every tablet on the network. Fine on a bench; do not leave it that way on the vehicle.
  • It copies only the zvision package — not zdeck, not tests.
  • It installs only zvision.service — not the deck, track or track-serve units, and not the Stream Deck udev rule.
  • It does not create /var/lib/zodiac/track, which the breadcrumb logger needs.

Credentials: none live on this box

The repository is public, so pulling needs no key at all — the HTTPS clone above is anonymous. Do not put a deploy key on the Jetson for read access; it would protect nothing that is not already public.

For pushing from the Jetson, use SSH agent forwarding rather than a resident key (ssh -A). Why not a read-write deploy key: this box lives unattended in a vehicle at Burning Man. A push credential stored on it is a push credential to main for anyone who walks off with the box or gets a shell on it. Agent forwarding grants that power only while you are logged in and leaves nothing behind. The trade-off is that unattended pushes are impossible — which is the correct answer for an art car.

4. Prove the bus with NO camera

cd /opt/zodiac/jetson
python3 -m zvision --source fake -v

You should see one line per frame (3 contacts -> N targets ZTHREAT;…). Now on a tablet, switch to the DRIVER concept — three moving contacts, one going red as it closes.

If that works, the network, multicast/broadcast and HUD are all proven

Everything after this is just swapping the fake detector for a real camera.

5. Attach the camera(s)

v4l2-ctl --list-devices          # find which /dev/videoN is which
v4l2-ctl -d /dev/video0 --all    # sanity: resolution/format

python3 -m zvision --source thermal --device /dev/video0 --hz 10 --hfov 160 -v

Walk in front of the camera — contacts should appear, their rel_az tracking left/right and size growing as you approach, on both the console and the HUD.

Sanity-check it physically

Stand at a known bearing (say 45° off the nose, paced out on the ground) and confirm the console's rel_az agrees. Do it once at the centre and once near the frame edge — the edge is where a wrong lens model shows up, and it is the same number that aims the tracker light. And note the settled FOV reference →

For the surround rig, repeat --camera per camera with its mounting bearing and optics. Measure each camera's az against the vehicle's actual nose, not by eye — an error there rotates every contact from that camera and swings the tracker light onto the wrong person. Rig declaration →

6. Make it permanent

sudo nano /etc/default/zvision
#   ZVISION_ARGS=--source thermal --device /dev/video0 --hz 10 --iface-ip 192.168.0.x
sudo systemctl restart zvision
journalctl -u zvision -f          # live logs
systemctl status zvision          # confirm active + auto-start
It comes back by itself after a power event

The unit is Restart=always, and three self-heal paths cover the playa power realities. A CameraStallGuard reopens a camera that wedges in select() at cold boot (~20 s, measured on hardware — the exact failure that once left the box “running but blind” for hours, emitting false all-clear). The broadcaster re-derives its subnet-broadcast target if it started before the DHCP lease. And olad is set to restart on crash. A cold power-on needs no human.

7. Bring up the DMX tracker light

Optional and independent of the camera — it is a downstream consumer of the same detection stream, so it needs no camera to test.

sudo jetson/scripts/install-ola.sh     # olad + ftdidmx plugin + CPU-pinned + on-boot

ola_dev_info                                  # find the ftdidmx device + port
ola_patch -d <device> -p <port> -u 0          # patch to universe 0
ola_set_dmx -u 0 -d 128,0,128,0,0,0,0,255     # pan/tilt/dimmer test
Do not use the older -d 128,0,128,0,255 form

It is still printed by install-ola.sh. In the 11-channel mode this fixture runs in, the fifth slot is the colour wheel, and 255 there means “auto colour change, fast”. The dimmer is channel 8, so that command pans and tilts a head that stays dark while spinning colours — indistinguishable from a dead fixture. The eight values above are pan, pan-fine, tilt, tilt-fine, colour, 0, 0, dimmer.

If the head still does nothing, check it completed its power-up homing sweep before blaming software. Detail →

python3 -m zvision --source fake --dmx fake -v   # logs target/pan/tilt/dim, no hardware
python3 -m zvision --source fake --dmx ola       # sends the universe to olad → dongle → head

Calibrate once on the vehicle: aim the head dead-ahead and set --dmx-pan-center to that fixture pan angle; --dmx-pan-gain (~1.0) maps camera az → pan. --dmx-no-sound disables the idle sound show.

8. Tuning on playa — laptop only

Assume the flashed image is final and the tuning is not. Nothing here needs a screen on the Jetson.

Access: the laptop joins the vehicle's travel-router WiFi and SSHes in — the Jetson is on Ethernet to the same router as the tablets and beacon, and no internet is required. Backstop if networking dies: the CP2102 serial console on J14 pins 3/4, 115200 8N1.

Your monitor is the tablets

Change a value, restart, watch contacts appear or vanish on the DRIVER HUD. That is a better feedback loop than a display on the Jetson, because you are seeing exactly what the driver sees.

# 1. Try it in the foreground first and watch the contacts scroll by
sudo systemctl stop zvision
python3 -m zvision -v --camera thermal:/dev/video0:az=0:fov=160:minarea=0.02

# 2. Happy? Validate the exact line before committing it to the service
python3 -m zvision --check <the same args>

# 3. Write it in and restart
sudo nano /etc/default/zvision      # ZVISION_ARGS=...
sudo systemctl restart zvision && journalctl -u zvision -f

Troubleshooting

SymptomCause / fix
HUD shows fake demo threats, not the Jetson'sTablet is not receiving — check the same subnet, and that the DRIVER source is network (fake is the fallback when no frames arrive)
Console shows frames, HUD shows nothingMulticast dropped at a router bridge — the broadcast leg should cover it; verify tablet and Jetson share a /24, check AP client-isolation is off
-> 0 targets in logsNo network route yet (network-online.target not reached) — check ip addr, set --iface-ip
could not open cameraWrong /dev/videoN, or cv2 missing on a non-JetPack box
Bearings compressed / stretched--hfov does not match the lens, or --lens has the wrong projection (fisheye = equidistant, ordinary = rectilinear); if the datasheet FOV is a diagonal, add --fov-ref d
One camera's contacts all sit at the wrong bearingThat camera's az= does not match how it is actually bolted on — measure it against the nose
One person shows up twice in a camera overlapRaise --merge-deg; lower it if two people standing close together get collapsed into one
no cameras opened, exit 3None of the rig's devices enumerated — check USB power / hub
A camera vanished but the run continuedBy design — check stderr for camera <name> failing, dropped; that arc is blind until it is back
Contacts flicker / bad idsThe motion detector is bring-up grade; the trained model replaces it. For now raise --hz and ensure a stable mount
--dmx ola runs but the head does not moveFirst: did it complete its power-up homing sweep? An un-homed head accepts DMX and silently discards it. Then: universe not patched, or the wrong universe. Confirm with ola_set_dmx -u 0 -d 128,0,128,0,0,0,0,255 — the trailing 255 is the ch8 dimmer; without it the head moves in the dark
DMX flickers / stuttersAnother OLA plugin is fighting for the FT232 (leave only ftdidmx), or olad is not CPU-pinned
olad will not grab the dongleKernel ftdi_sio may hold it as /dev/ttyUSB0; ftdidmx uses libftdi and should detach it — if not, modprobe -r ftdi_sio
Head moves but never pulses to musicNo $ZAUD arriving (beacon not broadcasting, or a different subnet), or --dmx-no-sound is set. The sound show only runs when idle
