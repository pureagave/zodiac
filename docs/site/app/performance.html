:app · the cockpit

Performance backlog

The cockpit draws a live Black Rock City map on a Compose Canvas at ~60 fps. RADAR is the worst case — a withFrameNanos sweep drives 60 fps redraws. Target hardware is the Amazon Fire HD 10: weak GPU and CPU, GC-sensitive.

Caveat for every item on this page

These are principled static-analysis wins (allocation, recomposition and overdraw reduction) from a 2026-06-14 render audit — not device-profiled. Confirm the felt improvement on a real tablet before and after. The behaviour-preserving subset of that audit already shipped; this page is what has not been done.

Naming note

The audit predates the concept rename. The concepts are now RADAR (MotionTrackerScreen, the sweep scope — the worst case here), MAP (InstrumentBayScreen) and DRIVER (DriverNightScreen, which did not exist when the audit was written and is not covered by any item below). The old A CRTVectorScreen and B PerspectiveScreen were deleted, so any item that referred to them has lost that half.

Tier 1 — cache the map's pixels, not just its geometry

The audit's central insight: the geometry pipeline is already well cached (ProjectedMap, viewport, label layouts), but nothing caches the rasterised pixels. Under the RADAR sweep, and in TILT mode, the entire CRT Skia call list — halo pair ×4 + 4 stroke paths + point batches + ~50 art circles + endpoint dots — replays every frame, even though the base map only changes at the 2 Hz GPS cadence. The 2026-06-14 pass removed the recomposition cost; the drawing cost remains.

The fix family is GPU layer promotion: render the static base map into a cached layer keyed so it only re-rasterises on camera change, then blit one texture per frame instead of replaying the call list.

Tier 2 — behaviour-preserving, pixel-identical

Verified behaviour-preserving and left for a focused pass. None need sign-off.

  • Reuse the wedge / cone Path objects — both allocate a fresh Path plus a 24-point trig loop inside the draw lambda every frame. The geometry depends on sweepDeg so it must re-trace per frame, but the allocation can go.
  • Reuse the ego-marker Path — same pattern. Compose draw is single-threaded, so a function-scoped reused Path is safe.
  • Narrow the RADAR format scope — MotionTrackerScreen reads the whole state at top scope for its String.formats, so the input slice buys nothing for those. Hoist the formatted strings into a child composable that takes only the fields it reads.
  • Batch major art — ~50 hollow drawCircles in DOT mode could batch into a single Path of addOvals. (Hollow stroke prevents drawPoints; a Path works.)
  • CockpitUiState stability — the data class embeds PlayaMap (which holds DoubleArrays) and NavigationCue, so the Compose compiler treats it as unstable and full-state child composables cannot smart-skip even when the reference is unchanged. Care: @Immutable is a correctness promise — getting it wrong causes missed recompositions that unit tests will not catch.
  • TextMeasurer hygiene — mostly allocation hygiene; lowest priority in this tier.

Tier 3 — changes the rendered look, needs sign-off

  • crtBeam = false on TrackerLitPalette drops 8 halo drawPaths and 3 endpoint drawPoints from the lit re-blit inside the wedge. The wedge still brightens features via the lit core strokes, so the M41A ping still reads — but it loses its doubled phosphor bloom and white corner dots. One-line change, biggest cost/effort ratio of the re-blit cuts. The cleaner alternative is the 1.2 layer cache, with no visual change. Pick one after seeing both on-device.

Measuring on device

Before and after any of the above, on a real Fire HD 10:

  • Jank percentiles: adb shell dumpsys gfxinfo org.pureagave.zodiac.control framestats. Reset with dumpsys gfxinfo <pkg> reset, exercise RADAR for ~30 s, dump.
  • Recomposition counts: Android Studio Layout Inspector while the sweep runs — the header and stat composables should tick at ~2 Hz, not 60 fps.
  • Compose stability: build with -Pandroidx.enableComposeCompilerMetrics=true and -Pandroidx.enableComposeCompilerReports=true.
  • Frame timing: a Macrobenchmark with FrameTimingMetric over a scripted RADAR session gives a repeatable P50 / P90 / P99.
  • GC pressure: Android Studio Profiler → Memory, watching allocation rate while RADAR runs.

The Fire is on the bench, so this whole backlog is unblocked. It is a profiling campaign, worth scoping before starting.
