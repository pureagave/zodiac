:app · the cockpit

Playa map and navigation

The centre of every concept renders a live Black Rock City map driven by the GPS source. Active year is a single source of truth: GoldenSpike.ACTIVE = Y2026. The 2026 city moved ~583 m south-west from 2025 but did not rotate — the 12:00 axis is still 45.0° true.

Data pipeline

GeoJSON assets → GeoJsonParser → typed PlayaMap → PlayaMapBinaryCache

The cache is a hand-rolled big-endian format (magic 0x504C4159 = PLAY, schema version 2, year in the header) written to a .tmp and renamed for atomicity. A magic, version or year mismatch is a silent miss that falls through to re-parsing the JSON.

PlayaMapRepository publishes the map first and writes the cache fire-and-forget, so serialisation never delays time-to-first-map. A load failure surfaces as MapLoadResult.Failed and is rendered with a RETRY control.

The parser reads both schemas: 2025 used type and a string width; 2026 uses source and an integer width_ft. That dual read is why the cache schema version is 2.

How that was found

The 2026 GIS renamed type→source/kind, width→width_ft and Name→name, which had left every street kind-less — an empty city model, so no cues and no routes — and every plaza label null. BundledGisTest now guards it and is the acceptance gate on a new dataset drop. The map-load error overlay that surfaces such a failure is visual-only and unverified: the state transitions are tested, but the rendering needs a device.

Geometry

PlayaProjection is equirectangular anchored on the Golden Spike (R = 6 371 000 m), with an allocation-free inline variant for the renderer's polyline walk. PlayaViewport is track-up with a configurable anchor, so TOP mode centres the ego and TILT mode anchors it to the lower third.

Active year

GoldenSpike.ACTIVE = Y2026. Every 2026 radial still puts the 12:00 axis at 45.0° true, verified against the shipped GIS — the 4:30 portal lands at exactly 180.0°.

Base assets are in app/src/main/assets/brc/2026/. The 2026 GIS ships no art layer; art and camp markers come from the BM API and stay hidden until BM releases the 2026 data, roughly three weeks pre-event.

Waiting on the world

location and location_string are null on all 332 art records. Everything else — artist, hometown, description, programme, images — is published and already in the app. When BM publishes placements, the map markers, the ART card and the approach detection all light up with no code change.

Unverified — the camp coordinate is an estimate

Camp.GALACTIC_RELAY is a geometric projection of “Heiau & 2:15” onto the 2026 grid, not a geocode. The authoritative placement comes from the BM API the Sunday before gates.

Outstanding — on-device address check

Typing 2:15 & H on the S9+ gives HEADING 112°, 1.6 km, identical to the HOME preset, which was verified 2026-08-08. The broader 2026 base-map check — typing a range of known addresses and confirming each lands on the right corner — remains outstanding, because the city has moved.

Shared destination across the fleet

When one tablet sets a drive-to target, every tablet adopts it over $ZNAV (239.7.7.30:10130), so the whole fleet's DRIVER HUD points the same way. The HUD's existing heading arch just starts pointing at the shared target — no new HUD UI was added, because adoption reuses the same NavigationController entry points a local set uses. Street labels are de-duplicated across the GIS's per-segment features so each logical street draws once.

Touch

Centre-viewport touch drives the map, not the vehicle: drag to pan, pinch to zoom, two-finger twist to rotate (ui/playamap/MapTouchInput). Heading and speed are set programmatically or by the GPS, never by tapping the viewport.

No automated coverage

The gesture state machine has no tests. Extracting a pure PinchSession from MapTouchInput, so it is unit-testable without awaitPointerEventScope, is an open task.

Playa discovery cache

Offline-first cache of the Burning Man API's art and camp records, stored in filesDir — not cacheDir, because Android may purge that and this is the only copy for up to 14 unattended days, with no bundled fallback the way the map has one.

  • Refreshes daily when there is internet; a failed or partial fetch never clobbers a good cache.
  • Atomic temp+rename write, copying PlayaMapBinaryCache.
  • refresh() merges by kind, so an art-only fetch cannot destroy cached camps.
  • A plausibility gate rejects placements more than 5 km from the spike — swapped or zeroed coordinates land thousands of km out.
  • One log line per refresh outcome, which on a Fire is the only way to answer “why are there no art markers”.
Unverified

The storage-location change has no test — ZodiacApplication wiring is not unit-testable without a Robolectric harness this repository does not have. Verified by review and compile only.

Without a BM_API_KEY in local.properties (as on CI) the key compiles to "" and the discovery fetch fails its HTTP call. That is not fatal: DiscoveryRepository keeps serving whatever is in its on-disk cache and logs the failure. Art and camp markers simply never appear.
