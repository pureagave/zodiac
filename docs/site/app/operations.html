:app · the cockpit

Displays and operations

The passenger carousel, the logging that has to survive fourteen unattended days, and the operational plumbing that makes a tablet on a dusty art car recoverable.

Passenger display

A self-running card carousel for riders: playa address, a mic-driven oscilloscope, thermal contacts around the vehicle, an impact “bump” gauge, trip odometer, sunrise/sunset countdown, nearest art.

  • A card with no data is dropped from the rotation rather than shown empty. A passenger display cycling through blank panels reads as broken hardware.
  • The “souls detected” card only appears on a genuinely LIVE vision feed — never on DEMO.
  • Enabled per device by a hidden top-right long-press, which also hides the concept switcher.

On-device postmortem logging

RollingFileLog writes zodiac.log plus four rotated segments under getExternalFilesDir("logs") — external app-specific storage, so it comes off a Samsung with a plain adb pull, no root and no debug build. Default bound is 512 KiB × 5 ≈ 2.5 MB.

It never throws, and it counts everything it loses

Write failures, rotation failures that could not honour the size cap, and lines aged out of the ring are all counted separately and surfaced in the log viewer's header. Silent loss would make the log a liar about its own completeness. A write that cannot be bounded is refused.

FileLogTree is the Timber tree. Writes go through a 256-line channel that drops oldest on overflow and drains on IO, so a log call from a render or sensor coroutine costs a trySend and cannot stall a frame. The uncaught-exception handler writes synchronously before the process dies.

Outstanding — one silent loss channel remains

FileLogTree's Channel(256, DROP_OLDEST) overflow is still uncounted. A burst silently loses lines before they ever reach RollingFileLog, so the on-screen counters cannot see them. This is the last silent loss channel in the logging path.

Tagged lifecycle events are the ones that actually get asked about: GPS source selection, NET→SYSTEM failover, vision feed transitions, transport connect, which path served the map, and discovery refresh outcomes.

Reading it back

adb pull /sdcard/Android/data/org.pureagave.zodiac.control/files/logs
This does not work on a Fire tablet

Fire OS denies shell access to /sdcard/Android/data, so the pull fails with “Permission denied”. On a Fire the hidden bottom-right long-press log viewer is the only way in — which is exactly why it exists.

Pre-rendered art imagery

tools/prerender_art.py bakes BM art thumbnails into the APK in the cockpit's phosphor treatment. Baked rather than styled at runtime because RuntimeShader is API 33+ while the passenger Fires are API 28, and the playa has no reliable internet. Re-run it when BM publishes new pieces.

Kiosk mode

Device-owner lock task, with the lockscreen and automatic OS updates disabled. The app locks itself on resume and no-ops when it has not been provisioned. The provisioning runbook →

Outstanding

Provisioning with a debug APK is a signature trap, the documented escape hatch likely does not work, and ota_disable_automatic_update is not an allowed key on API 34. Recorded as open.

Dead state

Deleted 2026-08-13

locationFallbackActive and commandError used to be written by the ViewModel and displayed by nothing — they looked wired and were not, exactly the shape of the mapLoadError bug that gave a blank viewport with no message when the GIS schema changed silently. Rob's call was final on both: no "on backup GPS" badge (recorded 2026-08-06 in SYNC.md), and every vehicle transport is fake so a real send failure cannot occur in production. Both fields and their sole writers were removed rather than wired up; a failed send is now logged via Timber instead of surfaced in UI state.

The breadcrumb, and its missing client

The Jetson runs a breadcrumb recorder (zvision.tracklog) that joins the telemetry group and writes daily NMEA-derived CSV, fsynced per row, served read-only over HTTP on :8087. The tablet-side puller is not written.

When it is, it should be understood as a partial copy, not a peer: Doze and process death punch holes in anything an Android app records or fetches on a schedule, which is precisely why the Jetson is authoritative.

Needs a decision, not a keyboard

Where the breadcrumb backs up to over the internet has deliberately not been chosen. It is a complete record of where the vehicle has been.
