The transport path, in full

Every vehicle transport is fake

RoutedVehicleGateway forwards commands to the selected adapter. FakeTransportAdapter.connect() transitions CONNECTING → (120 ms) → CONNECTED; send() while disconnected sets an ERROR phase and drops the command. FakeTelemetryRepository emits a deterministic 500 ms tick of heading / speed / thermal / mode that nothing on a real vehicle produces.

Real vehicle data does not travel this path at all. It arrives through NetworkLocationSource and NetworkThreatSource. The gateway is a boundary kept warm for a vehicle bus that does not exist yet.

By contrast the GPS location sources are real: there are working SystemLocationSource, BleLocationSource, UsbLocationSource and NetworkLocationSource implementations, and NET is verified end to end against the real beacon.

Known discrepancies

Recorded rather than quietly fixed, because fixing them is a code change.

Open bug — field-of-view reference

jetson/HARDWARE.md concludes, with a physics argument, that the Lepton Ultra Wide's quoted 160° is the diagonal, giving ±64° horizontal, and the tablet agrees: SurroundRing.COVERED_ARCS is -64f..64f. But zvision's --fov-ref defaults to h, and every documented example rig omits fovref=d, so the Python side computes bearings as if the camera covered ±80°.

The two sides currently disagree by up to 16° at the frame edge. Either the Python default flips or the tablet's covered arc widens; until then, treat edge bearings as unverified. Full detail.

Unresolved — DMX arbitration

zvision --dmx ola and zdeck must not run at the same time. At the tracker's frame rate a BLACKOUT would be overwritten within ~125 ms and would flicker rather than kill — which is worse than not having the key, because the operator would believe the light was off. This works today only because zvision's DMX output defaults to none. Detail.

Unverified
  • Camp coordinate is estimated, not geocoded. Camp.GALACTIC_RELAY is a geometric projection of “Heiau & 2:15” onto the 2026 grid. The authoritative placement comes from the BM API shortly before the event.
  • 2026 base map has not been fully checked on-device. The city has moved; typing a known address and confirming it lands on the right corner is outstanding.
  • Night legibility of the surround ring on the A54. Nobody has confirmed a #00421E rim and small hollow blips are readable at night brightness, through dust, by someone actually driving.
  • Tracker light aim. tilt_far_deg / tilt_near_deg / pan_center_deg / pan_gain are nominal placeholders and must be set on the actual mount before enabling real DMX output.
  • The R8-shrunk release APK has never been validated on a real tablet before fleet distribution.
  • The beacon's API 34/35 foreground-service branches are argued from documentation, not observed. The only beacon device on hand is API 29. Recorded as the biggest untested-on-hardware risk in that batch.
  • The map-load error overlay is visual-only and unverified — the state transitions are tested, but this project has no Compose UI harness, so the rendering (and whether the RETRY chip's tap conflicts with the map's pan/pinch pointer loop) needs a device.

The 2026-08-09 Android audit

Four independent reviews of the Android side — the :beacon sensor hub, GPS sourcing and fallback, the telemetry/state pipeline, and offline resilience — produced 20 findings (A1–A3, B1–B6, C1–C10). All 20 are closed as of 2026-08-10. The evidence is kept because several of the fixes are load-bearing design decisions that are easy to undo by accident:

FindingThe decision that must not be reverted
A1The brake gate reads effectiveSpeedKph (gpsSpeedKph ?: speedKph), not the debug chips' speed. Reverting that makes the alert un-fireable on a real drive — which is exactly what the audit found: ! BRAKE ! could never fire while actually driving.
A2RoutedThreatSource.demoEnabled has no default value on purpose, and production passes false. It once defaulted to true and production never overrode it, which put three fabricated contacts — one flagged as a collision course — on the driver's night HUD.
C2burnInScaffold.effectiveBacklight is the single write site for screen brightness; ambient auto-dim is folded in as a ceiling. A second writer is what the original bug was.
C6VTG, HDG and HDM are rejected as compass heading deliberately.
C7The beacon reports the peak of a shock impulse, and the tablet de-duplicates byte-identical $ZSHK lines within 200 ms.

The audit's own file:line references have since drifted; navigate by symbol name.
